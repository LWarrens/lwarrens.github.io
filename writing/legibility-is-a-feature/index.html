Legibility is a feature

The best internal tools do more than automate work. They make the system explain itself.

August 16, 20262 min read

  2. The interface is a theory of the system

The usual pitch for internal tooling is efficiency: fewer clicks, faster setup, less toil. All useful. None of it reaches the center of the problem.

The deeper value is legibility.

A developer environment is not merely slow when it takes too long to start. It is hostile when nobody can tell which dependency is missing, which background process stalled, or whether “ready” means the editor opened or the language server can actually answer a question.

An operational workflow is not safe because it has a confirmation dialog. It becomes safer when its state, preconditions, scope, and partial failures are visible to the person responsible for the outcome.

Automation without explanation creates new rituals#

Opaque automation often replaces one sequence of remembered commands with another: rerun the job, clear the cache, ask the person who built it, sacrifice a clean checkout under a full moon.

The work disappeared from view, but the uncertainty remained.

Good platform tooling should therefore answer three questions:

  1. What does the system believe is true?
  2. Why did it choose this action?
  3. What can the operator safely do next?

This changes the design. State stops being an implementation detail and becomes part of the interface. Diagnostics stop being the rubble left after a feature ships and become part of the feature itself.

The interface is a theory of the system#

Every dashboard, setup assistant, and CLI teaches a model, usually without admitting it. The names it exposes, the boundaries it draws, and the failures it groups together tell users what kind of machine they are dealing with.

When that model is accurate, people build intuition. When it is false, they build superstition.

The best tools I have worked on sat close to that boundary: IDE state assembled from language servers and local processes; cloud operations reconstructed from deployments, resource health, and configuration; network assets joined to geography and orchestration state.

The recurring problem was never simply “build a UI.” It was deciding what the system needed to reveal so that another person could reason about it.

That is not decoration around the engineering. It is the engineering.
